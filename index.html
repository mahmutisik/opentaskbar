What changed

1

Recycle Bin and network counters are polled off the UI thread

80–270 ms every 3 s · ~40 ms every 1 s0 ms on UI

The Recycle Bin state (SHQueryRecycleBin) was queried every 3 seconds on the UI thread and took around 100 ms inside the dock process; the network speed widget enumerated every adapter and its statistics every second. Together they froze the dock 5–6% of the time, which is what made hover, magnification and clicks feel sticky.

  • Recycle Bin: Task.Run, result applied on the UI thread, overlapping requests coalesced.
  • Network speed: sampled in the background, one sample at a time, rates computed from the real sample time (new ComputeRates helper with tests).
2

Launching and activating apps no longer block the dock

click handler avg 62 ms, up to 266 ms1 of 30 clicks ≥ 30 ms

Every activation attached the input queues of two apps and raised the window before asking for focus, which waits on both apps' UI threads. Launching a closed app ran ShellExecuteEx on the UI thread (100 ms to over a second).

  • A plain SetForegroundWindow is tried first: the dock click is the last input event, so Windows allows it. The old attach/raise path stays as the fallback.
  • Apps start from the thread pool; Process.Start runs ShellExecuteEx on its own STA thread there.
3

The background apps flyout opens immediately

~100 ms enumeration before every openshown from cache

The flyout appeared only after reading the tray registry snapshot and every running process. It now shows the last list at once, refreshes in the background and updates in place only if the list changed. The list is also warmed when the pointer reaches the button.

4

Running app icons load on a background thread

30 ms – 945 ms when a new app openedno UI freeze

Resolving a new app's icon (executable resources → Start menu image via IShellItemImageFactory → file icon) ran on the UI thread. RunningAppIconCache can now offload these lookups to one background STA thread; cache state stays on the UI thread and an IconLoaded event triggers a single refresh. Identity retries behave as before.

A regression found while testing (a Store app such as WhatsApp lost its freshly loaded image during the refresh it triggered) is fixed in the same commit and covered by a check.

How it was measured

A temporary diagnostic build (not part of this PR) wrote to perf.log:

ProbeWhat it shows
UI stall probeEvery 40 ms a no-op is posted at Input priority; anything that delays it ≥ 80 ms is a freeze the user can feel, logged with the operation that was running.
Scoped timersClick handlers, flyouts, previews, timers, widget ticks and icon loads, logged when ≥ 30 ms.
Dispatcher & message hooksEvery slow dispatcher operation and Win32 message, named by delegate or message and window class.
Click → resultTime from a press on the dock to the flyout or app window appearing.

Sessions were about 2.5 minutes each on the same machine. The “before” run included normal use (opening Settings, flyouts), the first “after” run was mostly idle; the periodic freezes it removes happen with or without use.

Looked at, not changed (yet)

AreaCostWhy it was left
Opening Settings0.5–0.7 sConstructor ~350 ms, layout ~180 ms, first frame ~130 ms. Keeping the window alive would make reopening instant, but controls are only filled from preferences in the constructor, so a hidden window could later save stale values.
Thumbnail preview35–90 msMostly resizing/positioning two transparent windows (~40 ms). Opens after a 300 ms hover delay, so the gain is small.
Rendering60–160 msSome render passes are expensive; the full-width dock is a layered window (AllowsTransparency), which copies every frame back from the GPU. A bigger architectural change.
Startup~3.5 s onceHappens in Win32 message handling during taskbar replacement; needs its own investigation.
Animations & hover delays—Kept as designed on purpose; shortening them is the last resort.
